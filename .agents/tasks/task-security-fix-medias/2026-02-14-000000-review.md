# MEDIUM security findings: CRON_SECRET gate, helmet/Swagger hardening, login token conditioning, collaborator declarative guards

This branch closes the four MEDIUM findings on top of `refatoracao`. FEAT-001 makes `CRON_SECRET` mandatory (≥32 chars) in production via the env validator while leaving the cron controller's constant-time header check intact. FEAT-002 adds `helmet` header hardening in `main.ts` and gates Swagger behind a non-production check. FEAT-003 stops leaking the raw session token in the login JSON body unless the caller signals Bearer intent, preserving the httpOnly cookie flow. FEAT-004 replaces the collaborator portal's per-handler manual auth with a class-level `ColaboradorAuthGuard` plus a per-handler password-changed guard, preserving the FEAT-003 `tokenVersion` revocation check and rewriting the revocation spec to exercise the guard directly.

Watch for: the FEAT-003 `wantsResponseToken` heuristic treats *any* `Authorization` header as Bearer intent (possible — a browser that ever sends a stale/empty `Authorization` header would receive the raw token in the body, though the known browser client does not send one). No blocking issues otherwise.

**Verdict**: APPROVED

## High-level view

The CRON_SECRET gate lives in `validate()` in `env.validation.ts` and fails fast at boot when `NODE_ENV=production` and the secret is missing or under 32 chars; the DTO field stays `@IsOptional()` so non-prod is unaffected. The controller's existing `timingSafeEqual` comparison is untouched, so the fix is purely a boot-time guarantee.

Helmet is applied before the global pipes with CSP and `crossOriginResourcePolicy` deliberately disabled (documented as needed for the CORS allowlist and inline DANFE PDF streaming), `frameguard: deny`, and HSTS only in production. Swagger document creation and `setup` are wrapped in `if (nodeEnv !== 'production')`, so the contract is not exposed in prod.

The login handler always returns `session.expiresAt` and now conditionally includes `session.token` only when the request carries an `Authorization` header or `x-auth-response-token: 1`. The httpOnly signed cookie is written unchanged, so browser sessions are unaffected while server-to-server Bearer callers can still opt in.

The collaborator portal moves to declarative guards: `@Controller('colaborador')` carries `ColaboradorAuthGuard` at class level, `login`/`logout`/`session` are marked `@ColaboradorPublic()`, and `perfil`/`recibos*` additionally carry `ColaboradorRequirePasswordChangedGuard`. `logo` and `trocar-senha` are authenticated but intentionally not password-gated. The revocation spec was rewritten to drive `ColaboradorAuthGuard.canActivate` with mocked collaborators, covering version mismatch, inactive, missing employee, no token, happy path, and the public-route bypass.

### CRON_SECRET production gate (FEAT-001)

The gate is enforced in `validate()` before `plainToInstance`, throwing `CRON_SECRET é obrigatório em produção e deve ter no mínimo 32 caracteres.` whenever `NODE_ENV === 'production'` and the value is not a string of length ≥32. Keeping the DTO field `@IsOptional()` while enforcing the production constraint imperatively is the right split: dev and test still boot without the secret, and the cron controller continues to answer `CRON_NOT_CONFIGURED` (not 401) when the secret is absent in those environments. The controller's `hasValidAuthorization` keeps the length-check + `timingSafeEqual` comparison, so the fix adds a boot-time guarantee without weakening the request-time check. `env.validation.spec.ts` covers missing, too-short, valid 32-char, and non-production-optional cases.

### helmet hardening and Swagger env gate (FEAT-002)

Helmet runs before the global validation pipe. CSP and `crossOriginResourcePolicy` are explicitly off with a comment tying the decision to the CORS allowlist and the inline DANFE PDF (`Content-Disposition: inline`) download; `frameguard: deny` and nosniff remain, and HSTS is production-only with a 180-day max-age plus `includeSubDomains`. Disabling CORP is a conscious trade-off for the inline PDF path rather than an oversight. Swagger's `createDocument`/`setup` are inside `if (nodeEnv !== 'production')`, closing the contract-exposure finding. `nodeEnv` is derived once and reused for both the helmet HSTS branch and the Swagger gate, so the two stay consistent.

### Login body token conditioned to Bearer intent (FEAT-003)

```ts
const wantsResponseToken =
  req.headers['authorization'] !== undefined ||
  req.headers['x-auth-response-token'] === '1';
// ...
session: {
  ...(wantsResponseToken && { token: sessionToken }),
  expiresAt: expiresAt.toISOString(),
},
```

The signed httpOnly cookie (`setSessionCookie`/`signSessionToken`) is written unchanged, so the browser flow is untouched; the cookie carries a different `token.hmac` format than the raw DB `sessionToken`, so withholding the body token does not affect cookie-based sessions. The author verified the web client reads only `data.user` and never `session.token`, so default browser logins lose nothing.

The heuristic is permissive on the `Authorization` branch: it keys off presence (`!== undefined`), not a valid non-empty Bearer value. Any caller that sends an `Authorization` header — including a browser that attaches a stale or empty one — receives the raw token in the JSON body, which is the exact exfiltration surface [MÉDIA] 7 set out to remove. The known browser client sends no such header, so this does not reopen the finding in practice; tightening it to require a non-empty Bearer token would remove the residual edge. Confidence: possible — depends on whether any browser caller can set `Authorization`, which the author checked and found none.

### Collaborator declarative guards preserving revocation (FEAT-004)

```
@Controller('colaborador')  ──  ColaboradorAuthGuard (class level)
  ├─ auth/login     @ColaboradorPublic()         → guard bypassed
  ├─ auth/logout    @ColaboradorPublic()         → guard bypassed
  ├─ auth/session   @ColaboradorPublic()         → guard bypassed
  ├─ logo           (auth only)
  ├─ auth/trocar-senha (auth only)               → NOT password-gated (it IS the change endpoint)
  ├─ perfil         + ColaboradorRequirePasswordChangedGuard
  └─ recibos*       + ColaboradorRequirePasswordChangedGuard
```

The design mirrors the main auth module: a class-level auth guard makes new handlers protected-by-default (the finding was that a new endpoint was public by omission), and the password-changed requirement is opt-in per handler so `logo` and `trocar-senha` stay reachable during first access. `ColaboradorAuthGuard` preserves the FEAT-003 revocation logic verbatim — rejects when `getRevocationState` is null, `!ativo`, or `tokenVersion !== payload.tokenVersion` — and populates `request.colaborador` consumed by the `@Colaborador()` param decorator and the password-changed guard. The password-changed guard reads `request.colaborador` and relies on running after the auth guard; since the auth guard is class-level and the password guard is method-level, NestJS runs them in that order, so the dependency holds. `logout` and `getSession` remain `@ColaboradorPublic()` and call `extractFromRequest` directly so they tolerate missing/invalid tokens, and `getSession` keeps its own inline revocation re-check.

`trocarSenha` reissues a fresh token after `changePassword` bumps `tokenVersion`, with `primeiroAcesso: false`, avoiding self-revocation of the current caller — the one place where the revocation check would otherwise invalidate the in-flight session.

The rewritten `colaborador-revocation.spec.ts` drives `ColaboradorAuthGuard.canActivate` with a mocked `ExecutionContext`, `Reflector`, `ColaboradorSessionService`, and `ColaboradorService`, covering version mismatch, inactive, missing employee, no token, the happy path (returns true and sets `request.colaborador`), and a `@ColaboradorPublic()` route that passes without calling `extractFromRequest`. Not tested: the method-level `ColaboradorRequirePasswordChangedGuard` has no direct unit test, and there is no integration test asserting the two guards compose in order on `perfil`/`recibos` — the ordering is correct by NestJS semantics but unverified by a test.
