# Security hardening of API ALTAs: global throttling, admin DTOs, revocable collaborator sessions

This branch (`security/fix-altas`) lands the three high-severity fixes from the scan: a global per-IP rate limiter via `@nestjs/throttler`, class-validator DTOs on the previously-unvalidated admin (`usuarios`) and `auth` endpoints, and a `tokenVersion`-based revocation mechanism for the stateless collaborator session token. Each fix lives in disjoint files and is additive. The collaborator change is the most involved: it adds a DB-backed version check to an otherwise stateless HMAC token so logout, password change, and future deactivation can invalidate outstanding tokens. Verification against the worktree holds the tsc baseline at exactly 22 pre-existing errors, builds clean, and leaves the test suite at 2039 passing with only the 2 pre-existing meta-presence failures.

Watch for: the throttler tracker keys on `req.ip` and `trust proxy` is deliberately not set, so behind a proxy the limit buckets per proxy IP, not per client (confirmed — flagged in-code as out of scope). Collaborator revocation adds one DB read per authenticated request where there was none before (confirmed — acceptable, worth noting). No blocking issues.

**Verdict**: APPROVED

## High-level view

The throttler is registered as `ThrottlerModule.forRoot([{ name: 'default', ttl: seconds(60), limit: 100 }])` with `ThrottlerGuard` wired as `APP_GUARD`. This is the correct v6 shape (named-throttler array, ttl in ms via `seconds()`). It sits alongside the existing per-identity `RateLimitService`, which is untouched, so login/forgot/reset keep their stricter identity-based limits while all routes gain a coarse IP ceiling.

The admin and auth endpoints previously typed their request bodies with inline interfaces, which the global `ValidationPipe` (whitelist + forbidNonWhitelisted) silently ignored — an authenticated ADMIN could persist an arbitrary `role`. The fix introduces real DTO classes and validates `role` against `['ADMIN','COLABORADOR']` both at the DTO boundary and again in the service before SQL. The `auth` login DTO correctly keeps `@IsString` (not `@IsEmail`) so the `identificador@kontabb.local` client flow still works.

Collaborator sessions were a stateless signed token with no server-side revocation: logout only cleared the cookie, and password changes left old tokens valid. The fix adds a `token_version` column to `funcionarios_rh` (additive migration 0027), embeds the version in the token, and compares it against the DB on every authenticated request. Password change and logout bump the version; `trocarSenha` reissues a fresh token with the new version so the acting user isn't self-revoked. Token verification stays synchronous (signature + exp only); the DB version/active check happens in the controller's now-async `requireAuth`.

### Throttler registration (FEAT-001)

The v6 API surface is used correctly: `forRoot` receives an array of named throttler configs, `ttl` is milliseconds produced by `seconds(60)`, and the guard is a global `APP_GUARD` provider added to a newly-created `providers` array on the root module. The imports array keeps its existing order, with the throttler slotted right after `ConfigModule.forRoot`. `@nestjs/throttler` is pinned at `^6.5.0` in `package.json`, matching the API shape.

Nothing in the auth or collaborator paths was touched by this feature, so the per-identity `RateLimitService` (login/forgot/reset/change-password/collaborator) continues to run independently. The two limiters are complementary: identity-based throttling guards credential endpoints, the global guard adds a blanket IP ceiling.

The one behavioral caveat is tracking. `ThrottlerGuard`'s default tracker reads `req.ip`, and `main.ts` deliberately does not call `app.set('trust proxy')`. Behind a proxy that terminates the connection, `req.ip` is the proxy's address, so the 100-req/60s bucket is shared across all clients rather than per-client. This is called out in an in-code comment as an infra adjustment outside this task's scope; whoever operates the deployment must configure `trust proxy` for the limiter to key on real client IPs.

### Admin and auth DTO validation (FEAT-002)

The core vulnerability was that `@Body()` typed by an inline TypeScript interface gives the runtime `ValidationPipe` nothing to validate against — no class, no decorators, so `whitelist`/`forbidNonWhitelisted` are inert and an ADMIN could inject any `role` string straight into the UPDATE. `CreateUsuarioDto`/`UpdateUsuarioDto`/`ChangePasswordDto` replace those interfaces with decorated classes, and `@ApiBody({ schema })` becomes `@ApiBody({ type })` so Swagger and validation agree.

Defense in depth is real here, not just at the edge: `usuarios.service.ts` re-checks `role` against `ROLES_SISTEMA` before touching SQL. `createSystemUser` returns `{ ok: false, code: 'INVALID_ROLE' }` (mapped to `BadRequestException` in the controller), and `updateSystemUser` throws only when `role` is defined, preserving the `COALESCE` semantics for partial updates where `role` is omitted. The parameterized queries are unchanged.

The subtle correctness point the author got right: `LoginDto.email` uses `@IsString`, not `@IsEmail`. The login path accepts `identificador@kontabb.local` synthetic addresses for the CLIENTE flow, which are not RFC-valid in the way `@IsEmail` expects; using `@IsEmail` here would have broken client login. `CreateUsuarioDto.email` (real system users) does use `@IsEmail`, which is the correct distinction.

### Collaborator session revocation via tokenVersion (FEAT-003)

The token is a stateless `base64url(JSON).HMAC` with an 8h TTL, so there was no server-side handle to revoke it — logout cleared the cookie but a copied token kept working, and password changes didn't invalidate anything. Rather than introduce a session table, the fix adds a monotonic `token_version` counter to the employee row and embeds it in the token:

```
login  ─> createToken({..., tokenVersion: N})      ─> cookie
request ─> verifyToken (sig + exp, sync, no DB)
        ─> getRevocationState(funcionarioId) ─> {ativo, tokenVersion: M}
        ─> reject if !row | !ativo | M !== payload.tokenVersion
change-password / logout ─> UPDATE token_version = token_version + 1
```

The division of labor is clean: `verifyToken` stays synchronous and purely cryptographic (signature + expiry), while the stateful check moves into the controller's `requireAuth`, which is now `async` and awaited at every call site (`trocarSenha`, `getPerfil`, `listRecibos`, `getRecibo`, `getReciboPdf`). The two endpoints that bypass `requireAuth` and call `extractFromRequest` directly — `getSession` and `getLogo` — got the same revocation check inlined, with `getSession` returning `{ user: null }` and `getLogo` throwing 401.

Two details worth confirming, both correct:

- **Self-revocation avoidance on password change.** `changePassword` bumps the version in the same UPDATE that sets the new hash, which would immediately invalidate the caller's own token. The controller re-reads the fresh version via `getRevocationState` and reissues a token carrying it, so the acting user stays logged in while every *other* outstanding token for that employee dies. Correct ordering.

- **Old tokens without the field.** Tokens minted before this change decode with `tokenVersion === undefined`. The comparison `revocation.tokenVersion !== payload.tokenVersion` evaluates `0 !== undefined` → true, so legacy tokens are rejected and forced to re-authenticate. This is the desired fail-closed behavior and it falls out naturally from the strict inequality. The `createToken` type (`Omit<ColaboradorTokenPayload, 'exp'>`) now requires `tokenVersion`, so no issue site can forget to pass it — enforced at compile time.

The `logout(funcionarioId)` and `changePassword` both increment via `sql\`${funcionariosRh.tokenVersion} + 1\``, an atomic DB-side increment rather than read-modify-write, so concurrent revocations don't race. A comment on `logout` flags that future desligamento/inativação routes must also bump `token_version` (or set `ativo = false`) — the right breadcrumb, since this mechanism only revokes where it's wired in.

Cost tradeoff: every authenticated collaborator request now does one indexed single-row read (`getRevocationState`) that didn't exist before. That is the inherent price of adding revocation to a stateless token and is acceptable; noted so it isn't a surprise under load.

### Migration shape (FEAT-003)

Migration `0027_tricky_namorita.sql` is a single `ALTER TABLE "funcionarios_rh" ADD COLUMN "token_version" integer DEFAULT 0 NOT NULL;` — purely additive, no destructive or cross-table changes. The `NOT NULL DEFAULT 0` backfills existing rows at version 0, which pairs correctly with the fail-closed rejection of legacy tokens. The baseline `0000` and all existing migrations are untouched; only `_journal.json` gains an appended idx-27 entry and a new snapshot is written. `integer` was already imported in `schema.ts`. `db:migrate` was correctly not run.

### Test coverage

The new `colaborador-revocation.spec.ts` covers the four decision branches of the revocation check — version mismatch, inactive employee, missing employee (null), and the happy path — plus `getSession` returning a null user when revoked. `usuarios.dto.spec.ts` asserts that out-of-whitelist roles are rejected and valid/partial payloads pass. Existing `auth.guard.spec.ts` and `session-token.spec.ts` stay green.

Not tested: the throttler guard itself (no integration test asserting a 429 after the limit), and the password-change reissue path isn't exercised end-to-end (the spec covers the reject branches of `requireAuth`, not the `trocarSenha` reissue-with-new-version sequence). Both are reasonable to defer given the manual verification, but the reissue path is the subtlest piece of logic in the branch and would benefit from a direct test.
